### 1.2 Current Model & Performance

| Component | Current Value | Problem |
|---|---|---|
| Base Model | `HuggingFaceTB/SmolLM2-360M-Instruct` | Too small; hallucinates even with correct RAG context |
| Fine-tuning | LoRA r=16, alpha=32, CPU, max_length=**128** | Context too short to capture full policy paragraphs |
| Training Data | 80 QA pairs (self-generated by 360M model) | Garbage-in/garbage-out: model trained on its own hallucinations |
| Embeddings | `sentence-transformers/all-MiniLM-L6-v2` (384-dim) | Works, but lower precision than modern alternatives |
| Vector Store | `torch.save()` flat file | No indexing; full linear scan |
| Retrieval | Hybrid: 0.5 × cosine + 0.5 × keyword | Retrieval is GOOD (scores 0.4-0.6); this is NOT the bottleneck |
| Inference | CPU, ~15-30 seconds/answer | Too slow for production |

### 1.3 Evaluation Results (Why Migration is Necessary)

The POC tested 3 configurations on 3 policy questions:
- **Config A** (Tuned model, no RAG): ❌ Fabricates non-existent legislation
- **Config B** (Base model + RAG): ❌ Fabricates monetary amounts even with correct context
- **Config C** (Tuned model + RAG): ❌ Still hallucinates despite having correct paragraphs

**Root cause**: The 360M model lacks the capacity to faithfully reason over retrieved text. The retrieval pipeline works correctly — the model is the bottleneck.

This is the PRIMARY data strategy. Use a high-quality external LLM API to generate expert-grade QA pairs from the 1,779 policy paragraphs already extracted.

#### [NEW FILE] `07_generate_training_data_api.py`

**Purpose**: Send each of the 1,779 policy paragraphs to Claude Haiku (or GPT-4o-mini) and ask it to generate 1-2 realistic QA pairs.

**Input**: The existing `vector_db.pt` file (contains all 1,779 paragraph chunks with text and paragraph IDs)
**Output**: `data/llm_generated_training_data.jsonl`
**Estimated API cost**: $5-15 (using Claude Haiku or GPT-4o-mini pricing)

```python
# Pseudocode / specification for the implementing AI:

"""
07_generate_training_data_api.py

REQUIREMENTS:
- Load vector_db.pt to get all 1,779 paragraph chunks
- For each chunk, call the LLM API with this prompt template:

SYSTEM_PROMPT = '''You are a DWP Decision Maker trainer creating training materials 
for new Child Maintenance Group staff. Based on the official policy paragraph below, 
generate 1-2 realistic questions that a Decision Maker trainee might ask, along with 
accurate, professional answers.

RULES:
1. Questions must be answerable SOLELY from the provided paragraph
2. Answers must cite the paragraph number (e.g., "As stated in Paragraph 18052...")
3. Use professional DWP terminology
4. Answers should be 2-4 sentences, factual, no speculation
5. If the paragraph is too short or vague for a meaningful question, output SKIP'''

USER_PROMPT = f'''Policy Paragraph {chunk['paragraph_id']}:
{chunk['text']}

Generate training QA pairs in this JSON format:
[{{"instruction": "question text", "output": "answer text"}}]'''

IMPLEMENTATION DETAILS:
- Use anthropic SDK (Claude Haiku) or openai SDK (GPT-4o-mini)
- Rate limiting: max 10 requests/second
- Retry logic: exponential backoff on 429/500 errors (max 3 retries)
- Resume capability: save progress every 50 paragraphs to a checkpoint file
  - On restart, skip already-processed paragraph IDs
- Quality filtering post-generation:
  - Reject QA pairs where answer < 30 characters
  - Reject QA pairs where answer contains "I don't know" or "not enough information"
  - Reject QA pairs where paragraph_id is not mentioned in the answer
- Output format: JSONL with fields: instruction, output, paragraph_id, source_doc, quality_tier
  - quality_tier = "high" for all LLM-generated data

ENVIRONMENT VARIABLES:
- ANTHROPIC_API_KEY or OPENAI_API_KEY (set via export or .env file)

EXPECTED OUTPUT: ~1,500-2,500 QA pairs in data/llm_generated_training_data.jsonl
"""
```

| **Epochs** | 3 | Standard for instruction tuning |

```python
"""
02_train_qlora_gpu.py — QLoRA Fine-Tuning with Unsloth on AWS GPU

CRITICAL IMPLEMENTATION NOTES FOR THE AI:

1. Use Unsloth's FastLanguageModel API — NOT raw transformers + peft.
   Unsloth wraps these and provides 2x speedup automatically.

2. The Unsloth training pattern is:

   from unsloth import FastLanguageModel
   from trl import SFTTrainer
   from transformers import TrainingArguments
   from datasets import load_dataset

   # Load model in 4-bit
   model, tokenizer = FastLanguageModel.from_pretrained(
       model_name = "mistralai/Mistral-7B-Instruct-v0.3",
       max_seq_length = 1024,
       load_in_4bit = True,
       dtype = None,  # Auto-detect (will use bf16 on A10G)
   )

   # Add LoRA adapters via Unsloth
   model = FastLanguageModel.get_peft_model(
       model,
       r = 16,
       lora_alpha = 32,
       target_modules = ["q_proj", "k_proj", "v_proj", "o_proj",
                          "gate_proj", "up_proj", "down_proj"],
       lora_dropout = 0,
       bias = "none",
       use_gradient_checkpointing = "unsloth",  # Unsloth's optimized checkpointing
       random_state = 42,
   )

3. Data formatting function — convert each sample to the model's chat template:

   def formatting_func(examples):
       texts = []
       for instruction, output in zip(examples["instruction"], examples["output"]):
           messages = [
               {"role": "user", "content": instruction},
               {"role": "assistant", "content": output},
           ]
           text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=False)
           texts.append(text)
       return {"text": texts}

4. Training with SFTTrainer (from trl library):

   trainer = SFTTrainer(
       model = model,
       tokenizer = tokenizer,
       train_dataset = train_dataset,
       eval_dataset = val_dataset,       # For validation loss monitoring
       dataset_text_field = "text",
       max_seq_length = 1024,
       dataset_num_proc = 2,
       packing = True,                   # Packs multiple short samples into one sequence
       args = TrainingArguments(
           output_dir = "./training_output",
           per_device_train_batch_size = 4,
           gradient_accumulation_steps = 4,
           num_train_epochs = 3,
           learning_rate = 2e-4,
           warmup_ratio = 0.03,
           lr_scheduler_type = "cosine",
           bf16 = True,
           logging_steps = 10,
           save_strategy = "steps",
           save_steps = 100,             # Frequent saves for spot instance resilience
           save_total_limit = 3,
           eval_strategy = "steps",
           eval_steps = 100,
           optim = "adamw_8bit",
           seed = 42,
           report_to = "wandb",          # Optional: set to "none" to disable
       ),
   )

   trainer.train()

5. Save the trained adapter:

   model.save_pretrained("./trained_models/mistral-7b-cmg-qlora")
   tokenizer.save_pretrained("./trained_models/mistral-7b-cmg-qlora")

6. ALSO save merged model for vLLM inference later:

   model.save_pretrained_merged(
       "./trained_models/mistral-7b-cmg-merged",
       tokenizer,
       save_method = "merged_16bit",  # Full precision merged model
   )

COMMAND LINE INTERFACE:
- The script should accept these arguments via argparse:
  --model_name     (default: "mistralai/Mistral-7B-Instruct-v0.3")
  --train_data     (default: "data/train_split.jsonl")
  --val_data       (default: "data/val_split.jsonl")
  --output_dir     (default: "./trained_models/mistral-7b-cmg-qlora")
  --max_seq_length (default: 1024)
  --epochs         (default: 3)
  --batch_size     (default: 4)
  --learning_rate  (default: 2e-4)
  --lora_r         (default: 16)
  --use_wandb      (default: True)

This allows benchmarking Qwen3 by simply running:
  python 02_train_qlora_gpu.py --model_name "Qwen/Qwen3-8B" --output_dir "./trained_models/qwen3-8b-cmg-qlora"

RESUME TRAINING:
- If the script detects a checkpoint in output_dir, it should automatically resume
  from the latest checkpoint (for spot instance resilience)

S3 SYNC:
- After training completes, automatically run:
  os.system("bash scripts/sync_to_s3.sh")
"""
```

## 6. PHASE 4: RAG PIPELINE UPGRADES

**Duration**: 2-3 days
**Dependencies**: Phase 1 complete (can run in parallel with Phases 2-3)

### 6.1 Embedding Model Upgrade

| Current | Upgrade |
|---|---|
| `sentence-transformers/all-MiniLM-L6-v2` | `BAAI/bge-base-en-v1.5` |
| 384 dimensions | 768 dimensions |
| General purpose | Better on domain-specific retrieval benchmarks |

### 6.2 Vector Store Upgrade

| Current | Upgrade |
|---|---|
| `torch.save()` — flat tensor, linear scan | FAISS `IndexFlatIP` (inner product, since we L2-normalize) |

### 6.3 Chunking Upgrade

| Current | Upgrade |
|---|---|
| Split by paragraph ID regex (variable length) | Same paragraph ID split BUT with sub-chunking for long paragraphs |

## 11. TROUBLESHOOTING REFERENCE

| Problem | Solution |
|---|---|
| CUDA OOM during training | Reduce batch_size to 2, reduce max_seq_length to 512 |
| Spot instance interrupted mid-training | Run `scripts/restore_from_s3.sh`, then re-run training (it auto-resumes from checkpoint) |
| `bitsandbytes` not found or CUDA error | Ensure `pip install bitsandbytes` is run inside the conda env with CUDA available |
| FAISS not finding GPU | Install `faiss-gpu` not `faiss-cpu`: `pip install faiss-gpu` |
| Model download fails | Check HuggingFace token: `huggingface-cli login` (needed for gated models, but Mistral and Qwen3 are public) |
| Unsloth import error | Reinstall: `pip install "unsloth[colab-new] @ git+https://github.com/unslothai/unsloth.git"` |
| vLLM compatibility issue | vLLM requires specific PyTorch/CUDA versions. Use the version matching your DLAMI's CUDA. |
| Training loss not decreasing | Check data format: ensure each sample has "instruction" and "output" fields. Check learning rate (try 1e-4). |
| Validation loss increasing | Overfitting — reduce epochs to 2 or increase training data. Enable early stopping. |
